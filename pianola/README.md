# Pianola

Imports a score, compiles it into a timeline of note events, and (from phase 2)
plays it back on an 88-key keyboard drawn in the browser.

Odoo 19.0 Community, LGPL-3, no Enterprise dependency, no CDN, no extra Python
package.

## Layers

| Layer | Where | Depends on Odoo |
|---|---|---|
| Ingest | `models/music_score.py`, `wizard/` | yes |
| Compile | `lib/musicxml/` | **no** |
| Playback | `static/src/` | yes (phase 2) |

The compiler is deliberately Odoo-free. It reads MusicXML bytes and returns a
`Compilation`: a flat list of note events with absolute times in seconds, plus
a pedal track, a measure map and a tempo map.

Run it on its own:

```bash
python3 pianola/tools/compile_score.py score.musicxml
python3 pianola/tools/compile_score.py score.mxl --json out.json --midi out.mid
```

Run its tests without a database:

```bash
python3 pianola/tools/run_lib_tests.py
```

Run everything, including the ORM tests:

```bash
odoo -d <db> -i pianola --test-enable --stop-after-init
```

## What the compiler handles

Pitch
: `<alter>` is taken as written — MusicXML has already resolved the key
  signature and accidentals, so applying the key again would double the
  alteration. Double sharps and double flats work. The written spelling is
  kept next to the MIDI number, so F♯ and G♭ still read differently even
  though they are the same key.

Time
: `<divisions>` is renormalised to 480 ticks per quarter, so it may differ
  between parts and change mid-piece. Tempo comes from `<sound tempo>` and
  from metronome marks, including dotted beat units, and is integrated segment
  by segment rather than averaged. Dots and tuplets need no special handling:
  `<duration>` already accounts for them, and `<time-modification>` is
  notation. Pickup bars are not padded out. A fermata inserts a hold in the
  clock rather than pretending to be a tempo change.

Structure
: Repeats are unfolded before anything else runs — forward and backward
  barlines, repeat counts, alternative endings, D.C., D.S., segno, coda, To
  Coda and Fine, including the ones written only as words. Anything the
  unfolder cannot read is logged and the piece plays in written order.

Polyphony
: `<backup>` and `<forward>` move a per-part cursor, which is what keeps the
  left hand under the right instead of after it. `<chord>` shares the previous
  onset and does not advance the cursor. Several voices per staff, and
  cross-staff notes, follow the `<staff>` element rather than the pitch.

Ties and articulation
: A tie merges into a single event, across bar lines and across repeat
  boundaries. A slur does not. Staccato and friends shorten the *sounding*
  duration without moving the next onset.

Dynamics and pedal
: Marks map to velocity and hold until the next one. Hairpins interpolate
  linearly to the next explicit mark. The sustain pedal is a track of its own,
  so the audio layer can hold notes past their written length without the
  score having to lie about their duration.

## What it does not handle yet

Ornaments (trill, mordent, turn, appoggiatura, arpeggio) and grace notes are
**dropped and logged**, not played as zero-length notes. They are phase 4.
MIDI and PDF sources are refused with a clear message; PDF is phase 3.

Anything unknown ends up in `parse_log` on the score, with a count, instead of
raising.

## Data model

`music.note` is a real table so optical-recognition mistakes can be corrected
by hand, which is where the module earns its keep. The player never reads it:
it reads `playback_json`, a compact cached payload regenerated by the
**Recompile** button. Notes are inserted with a single batched `create()`.

## Tests

`tools/run_lib_tests.py` runs everything that does not need a database. The
MIDI regression test is skipped until you drop reference files into
`tests/fixtures/` — see the README there.
